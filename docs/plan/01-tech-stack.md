# Tech Stack

All choices are constrained by the PRD's hard requirement: **$0 ongoing cost.** Every infra row below names a provider with a genuinely perpetual free tier (not a trial), and states its real limitation rather than hiding it.

## Frontend

| Concern | Choice | Why | Alternatives considered |
| --- | --- | --- | --- |
| Framework | **Next.js 14+ (App Router), TypeScript** | User-specified. App Router gives server components for the landing page (fast, SEO-friendly, no client JS needed) while the authenticated app uses client components freely. Deploys natively and freely on Vercel. | Remix (also good, smaller ecosystem); plain Vite SPA (loses SSR for the landing page, worse SEO) |
| Styling | **Tailwind CSS**, user-specified, + **shadcn/ui** (Radix primitives, copy-in components, not a runtime dependency) | Tailwind for velocity and consistency; shadcn/ui gives accessible, unstyled-by-default primitives (dialog, dropdown, tooltip, etc.) that we own and can restyle to a distinctive brand rather than looking like a template. | Chakra/MUI (impose their own visual identity, harder to make "distinctive") |
| Component architecture | Feature-folder structure (`features/monitors`, `features/incidents`, …) over strict atomic design | Matches how the product actually decomposes (see `00-frontend-architecture.md`); avoids over-abstracting a small MVP | Atomic design (adds indirection with no payoff at this size) |
| Client/UI state | **Zustand** | Minimal boilerplate for the small amount of pure client state (sidebar collapsed, active tab, wizard step) | Redux Toolkit (too much ceremony for what's needed) |
| Server state / data fetching / caching | **TanStack Query** | Handles caching, refetch-on-interval (used for the "live" dashboard polling instead of WebSockets, see `03-monitoring-engine.md`), retries, and loading/error states with far less hand-written code than raw `fetch` + `useEffect` | SWR (comparable; TanStack Query's devtools and mutation ergonomics are a better fit for a CRUD-heavy app) |
| Forms | **React Hook Form** | Uncontrolled-by-default, fast with the long monitor-creation form (Section 9.1 of the PRD, single scrollable form) | Formik (more re-renders, less actively maintained) |
| Validation | **Zod** | Runtime + compile-time validation from one schema; mirrors the shape the backend's DRF serializers validate, keeping client and server validation intentionally redundant but never contradictory | Yup (weaker TS inference) |
| API communication | Typed client generated from the backend's OpenAPI schema (`openapi-typescript` + a thin fetch wrapper), consumed through TanStack Query hooks | Backend is the source of truth for the contract (DRF + drf-spectacular generates the OpenAPI schema); frontend never hand-writes response types | tRPC (would require the backend to be TypeScript too — it isn't) |
| Charts | **Recharts** | Composable, good defaults, handles the response-time/uptime/analytics charts in Section 6.5 of the PRD without heavy custom D3 work | visx (more power, much more code for the same result at this scope) |
| Tables | **TanStack Table** | Headless, pairs with shadcn/ui for the monitor list, incident list, check-history table | Building tables by hand (fine for one, painful across five) |
| Auth (client) | Backend-issued short-lived JWT access token (in memory) + httpOnly refresh cookie set by the backend; Next.js middleware gates routes on cookie presence, the backend re-validates on every request | Backend is a separate service from the Next.js app, so NextAuth/Auth.js (designed for when Next.js itself issues sessions) doesn't fit cleanly — a backend-owned token pair is simpler and keeps auth logic in one place | NextAuth/Auth.js (awkward fit for a decoupled API) |
| Animations | **Framer Motion** | Landing page section transitions, subtle dashboard micro-interactions | CSS-only (fine for simple cases, used where Framer would be overkill) |
| Icons | **lucide-react** | Pairs natively with shadcn/ui, consistent stroke style | Heroicons (also fine; lucide has a larger set) |
| Testing | **Vitest** + React Testing Library (unit/component), **Playwright** (E2E) | Vitest is fast and Vite-native (Next.js supports it); Playwright covers real cross-browser E2E for the critical flows in `05-testing-deployment-devex.md` | Jest (slower, more config for the same result) |

## Backend

| Concern | Choice | Why | Alternatives considered |
| --- | --- | --- | --- |
| Language / framework | **Python 3.12 + Django 5 + Django REST Framework** | User-specified. DRF gives serializers (validation + typed shape, the Zod equivalent), viewsets/routers, session and token auth, built-in throttling (used directly for API rate limiting, `04-security.md`), and a mature admin panel that doubles as a free internal ops tool (inspect monitors/incidents without building an admin UI). Django's ORM natively supports `select_for_update(skip_locked=True)`, which is exactly the primitive the monitoring engine's job queue needs — no separate queue library required at MVP scale. | FastAPI (faster to write, but DRF's batteries — admin, throttling, auth, ORM — remove real work at this scope); Flask (too little structure for a project this size) |
| API style | REST, versioned (`/api/v1/...`), OpenAPI 3.1 schema auto-generated via **drf-spectacular** | Matches the PRD's explicit "REST API" requirement (Section 6.10); the generated schema is what the frontend's typed client is built from — one source of truth, not two hand-maintained ones | GraphQL (no PRD requirement for it; adds real complexity — query complexity limits, N+1 handling — for no MVP benefit) |
| Database | **PostgreSQL** | JSONB for flexible per-monitor-type config, strong indexing for time-series check data, mature `skip_locked` support, and a free managed tier is easy to find | MySQL (weaker JSON support); SQLite (fine for local dev, not for a scheduler process with concurrent writers) |
| Database hosting | **Neon** (serverless Postgres, free tier, branching) | Free tier is genuinely perpetual, and database branching is useful for testing migrations against a copy of real data | Supabase (also viable — free Postgres plus built-in storage; either works, Neon is the primary pick, Supabase is the fallback if object storage becomes a real need) |
| ORM / migrations | **Django ORM + built-in migrations** | No separate tool needed — this is Django's own, well-tested system; one fewer dependency versus bringing in Prisma/SQLAlchemy-style tooling | N/A — bringing in a second ORM alongside Django's own would be pure overhead |
| Auth | **Custom Django user model** (swapped in from day one — retrofitting later is painful) + `djangorestframework-simplejwt` for API JWTs (short-lived access + rotating refresh) + a minimal hand-written GitHub OAuth2 code-exchange view | A custom user model on day one avoids a painful later migration. A few dozen lines of GitHub OAuth code avoids pulling in `django-allauth`, which assumes a server-rendered, session/template-based app — this backend is a pure JSON API for a separate SPA | `django-allauth` (heavier, more assumptions than a single-provider OAuth flow needs) |
| Scheduler / background jobs | **Django management commands** (`run_scheduler_once`, `run_notifications_once`) that do ONE pass — claim due work from Postgres via `select_for_update(skip_locked=True)`, execute it, and exit — invoked via a signed internal HTTP endpoint on a **GitHub Actions cron schedule** (every 5 min, matching the minimum check interval), not run as an always-on process | Render's free tier has no always-on Background Worker or Cron Job (only free Web Services, which sleep after 15 min idle — confirmed against Render's own docs). A triggered, single-pass command sidesteps that entirely, and the periodic trigger request has the added benefit of keeping the free web service from sleeping (a request every 5 min never accumulates 15 idle minutes). No external broker needed either way. | An always-on process (works on Fly.io, not on Render's free tier); Celery + Redis (deferred to V2 regardless of host — see the callout below) |
| Concurrency (per triggered pass) | Python `ThreadPoolExecutor` (bounded pool, e.g. 20 workers) running synchronous `httpx` requests, within the single request/response cycle of the triggered endpoint | Checks are I/O-bound; a thread pool gets real concurrency without the async/sync-ORM friction Django still has in places. Simple to reason about and debug — a deliberate "boring and provable" choice | `asyncio` + async Django views (Django's async ORM support is still maturing in places; not worth the complexity here) |
| Multi-location probers | **Cloudflare Workers** (free tier, 100k requests/day) in 2–3 regions; the Django endpoint calls them over signed HTTP during its triggered pass and gets a result back synchronously | Genuinely no sleep/cold-start concept — a Worker responds instantly whether it was "idle" or not, which a Render free Web Service cannot promise (its ~1 min spin-up would blow through any per-check timeout budget). Probers never touch the database or business logic — they just execute one check and return JSON. | FastAPI services on Fly.io regions (works, but reintroduces an always-on-adjacent hosting dependency this plan is otherwise avoiding by using Render) |
| Caching | In-process (Django's local-memory cache) for hot aggregates with short TTL | No Redis needed yet at this scale; revisit if/when dashboard read load actually requires it | Redis cache (deferred to V2 alongside Celery, if it becomes needed) |
| Notifications | In-process dispatch via the same `skip_locked` pattern, logged to a `NotificationDelivery` table for retry/audit | Consistent with the scheduler's own queue-less design — one pattern, not two | A separate notification microservice (unnecessary at this scale) |
| Email | **Resend** (free tier: 3,000/month, 100/day) | Clean API, good deliverability reputation for a new sending domain, generous enough for single-user + status-page subscriber volume | Brevo, Mailgun sandbox (both fine fallbacks if Resend's limits are ever hit) |
| File/object storage | Not required for MVP (status-page logo can be a URL or small base64); **Cloudflare R2** free tier noted as the pick if/when real uploads are needed | Avoid adding a storage dependency before there's an actual file to store | AWS S3 free tier (time-limited, not perpetual — rejected on the $0 constraint) |
| Realtime | Polling via TanStack Query refetch intervals, not WebSockets | At 5-minute-minimum check intervals, near-real-time polling is indistinguishable from a live socket to the user, and it avoids Django Channels + a second ASGI deployment concern entirely for MVP | Django Channels (deferred to V2 if a genuinely real-time feature demands it) |
| Testing | **pytest + pytest-django**, **factory_boy** for test data | Idiomatic modern Django testing; factories keep test setup for Monitor/Incident/etc. DRY across the large number of scenarios in `05-testing-deployment-devex.md` | Django's built-in `unittest`-style `TestCase` (works, but pytest's fixtures and parametrization reduce boilerplate significantly here) |

> **Callout — Celery is the "expected" choice, and it's deliberately not the MVP choice.** Most production Django apps use Celery + Redis/RabbitMQ for background work, and a reviewer familiar with Django will look for it. The call here is explicit: at this project's actual scale (one user, dozens of monitors, 5-minute-minimum intervals), a Postgres-native queue removes an entire piece of paid-adjacent infrastructure (Redis) with no functional loss, and it's a legitimate, well-known pattern (`SKIP LOCKED` job queues are documented Postgres practice, not a hack). It's also the only realistic option on Render's free tier specifically, since Celery needs a broker (Redis) *and* a worker process that stays running to consume from it — neither is free there. The roadmap (`06-roadmap.md`) states the concrete trigger for migrating to Celery + Redis in V2: sustained scheduler lag, a real need for cross-machine job distribution, or moving off Render's free tier to a host where an always-on worker is affordable.

## Infrastructure

| Layer | Choice | Free-tier reality | Notes |
| --- | --- | --- | --- |
| Backend hosting (API) | **Render** (free Web Service, Docker deploy) | Free tier sleeps after 15 min idle and has no free always-on worker/cron — mitigated by the GitHub Actions cron trigger doubling as a keep-alive (above). Chosen because it's what this project uses; Fly.io remains a documented alternative if the sleep/cold-start trade-off ever becomes a real problem. | Fly.io (perpetual always-on free VMs, no sleep — the better fit for a scheduler in isolation, but not the chosen host here); Railway (trial-credit-based, not perpetual) |
| Scheduler trigger | **GitHub Actions** scheduled workflow (`cron:`) | Free (generous minutes even on a private repo), already used for CI, no new account needed | A separate free cron service (cron-job.org etc.) — more moving parts for no benefit |
| Multi-location probers | **Cloudflare Workers** | Free tier: 100k requests/day, no sleep | See the stack table above |
| Frontend hosting | **Vercel** | Free tier is generous and effectively unlimited for a low-traffic MVP | Best-in-class Next.js support, zero-config deploys from GitHub |
| Database hosting | **Neon** | Free tier: serverless Postgres, autoscales to zero when idle. Already provisioned and migrated. | Supabase as a documented fallback |
| Email | **Resend** | Free tier: 3,000 emails/month | See backend table above |
| DNS | Domain registrar's free DNS, or **Cloudflare** (free) if proxying is wanted | Cloudflare adds free CDN/SSL in front of the domain if desired later | Not required for MVP, noted for V2/marketing-site scaling |
| SSL | Automatic, free (Vercel + Render both auto-provision Let's Encrypt certs) | No manual cert management | |
| CI/CD | **GitHub Actions** | Free minutes are generous for a solo-dev private repo; unlimited for public | Lint/typecheck/test on every PR; deploy-on-merge (Vercel via its GitHub integration, Render via its own GitHub integration); a separate scheduled workflow triggers the scheduler/notification passes (above) |
| Error tracking | **Sentry** | Free tier: 5,000 errors/month | Genuinely useful at this scale, not a toy |
| Logging | Render's built-in dashboard log aggregation (short retention) for MVP | Free but limited retention (days, not months) | Axiom or Better Stack Logs free tiers noted as the V2 upgrade if longer retention matters |
| "Who watches the watcher" | A single free external check (even UptimeRobot's own Free plan) pinging RootPulse's own `/health` endpoint | RootPulse cannot detect its own total outage from inside itself | Cheap irony, real necessity |

## What's deliberately not here (per PRD Section 5.2 / 11)

No payment provider, no SMS/voice provider (Twilio etc.), no licensed dependency-incident dataset, no LLM API, no Redis/Celery at MVP, no WebSocket infrastructure, no multi-tenant/organization layer. Each has a stated trigger for reconsideration in `06-roadmap.md`, not a silent omission.
